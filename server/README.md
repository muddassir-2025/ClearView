# ClearView Good Post — Backend

A WhatsApp-Channels-style broadcasting service for the ClearView Android app.
Node 22 + TypeScript + Express 5, **Neon PostgreSQL** for structured data,
**Amazon S3** for media, deployed on **Render**.

The Android app is in the repository root (`app/`). **This `server/`
directory is the whole backend** — it is a separate deployable, not part of
the Gradle build.

---

## 1. What you must provide

| # | Value | Where it comes from | Needed by |
|---|---|---|---|
| 1 | `DATABASE_URL` | Neon → Dashboard → Connection string → **Pooled** | now |
| 2 | `DATABASE_URL_DIRECT` | Neon → same panel → **Direct** (no `-pooler`) | now |
| 3 | `SUPER_ADMIN_EMAIL` + `SUPER_ADMIN_PASSWORD_HASH` | You choose; §3 below | now |
| 4 | `AWS_REGION` | e.g. `eu-central-1` | media only |
| 5 | `AWS_S3_BUCKET` | S3 bucket name | media only |
| 6 | `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | IAM user or role (§4) | media only |
| 7 | `PUBLIC_BASE_URL` | Your Render URL, e.g. `https://clearview-goodpost-api.onrender.com` | share links |
| 8 | `ADMIN_CONTACT_EMAIL` | the address readers are told to write to | now |
| 9 | `CORS_ORIGINS` | only if a browser client ever exists | optional |

Rows 4–6 are the ONLY optional ones, and their absence is a supported state:
text and link posts work on a deployment with no bucket (§22). Rows 1–3 are not
optional in production — `src/env.ts` refuses to boot without an administrator,
because a service nobody can sign in to is a channel list that never changes.

`JWT_SECRET`, `JWT_REFRESH_SECRET` and `PHONE_HASH_PEPPER` are **generated by
`render.yaml`** (`generateValue: true`) — do not invent them. For local
development, generate your own:

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

> **Never put any of these in the Android app, and never commit them.** The
> Android client only ever needs the backend base URL (see §6).

## 2. Neon PostgreSQL setup

1. Create a project at [neon.tech](https://neon.tech) (any region close to
   your Render region — pairing `frankfurt` with `aws-eu-central-1` keeps
   database round-trips short).
2. Copy **two** connection strings from the dashboard:
   - the **pooled** one (host contains `-pooler`) → `DATABASE_URL`
   - the **direct** one → `DATABASE_URL_DIRECT`
3. TLS is required; both strings end in `?sslmode=require`.

**Why two URLs.** The running service uses the pooled host so many short
requests share few Postgres connections. Migrations use the direct host: a
transaction-pooling endpoint may route the statements of one logical session
across different backends, which breaks both DDL and the session-level
advisory lock the migration runner depends on (§42).

### Migrations

Never mutate the production schema at startup (`server/src/index.ts` does not
do this, by design). Migrations are forward-only SQL files in `migrations/`,
applied by `src/migrate.ts`:

```bash
npm run migrate          # local, via tsx
npm run migrate:prod     # compiled, via dist/migrate.js — what Render runs
```

The runner:

- wraps **each file in its own transaction** — a migration fully applies or
  not at all;
- takes a **session advisory lock** so two concurrent runs cannot race (a
  Render pre-deploy can overlap a still-draining instance);
- records a **SHA-256 checksum** of each applied file and refuses to run if an
  applied file changed. Migrations are immutable — add a new file instead;
- is **idempotent** — re-running with nothing to apply exits cleanly.

### Backup / rollback

Neon keeps point-in-time-restore history per branch, which is the rollback
mechanism: restore the branch to a timestamp rather than writing `DOWN`
migrations. Before a risky migration, create a Neon branch of production
first, and run the migration against that branch to verify it.

## 3. The first administrator (§17)

Good Post has **no viewer accounts**. Readers open the app and read; nothing is
signed up for, so there is no Firebase project, no phone verification, no email
sign-in code and no push registration anywhere in this service.

The only credential in the product is an administrator's, and there are exactly
two roles:

| Role | Scope |
|---|---|
| `super_admin` | Every channel, every post, every administrator. Created here. |
| `channel_admin` | One channel. Created from the app by a super admin, when the channel is. |

The first super administrator comes from the ENVIRONMENT and is reconciled at
every boot:

```bash
# A bcrypt hash — the value the database would store anyway.
npm run create-admin -- --generate        # generate a password, print it once
```

Or set them yourself:

```bash
SUPER_ADMIN_EMAIL=you@example.com
# Generate: node -e "console.log(require('bcryptjs').hashSync(process.argv[1], 12))" 'your-password'
SUPER_ADMIN_PASSWORD_HASH='$2b$12$…'
SUPER_ADMIN_DISPLAY_NAME=Good Post Admin
```

`SUPER_ADMIN_PASSWORD` (plaintext, hashed once at boot) is accepted as an
alternative for a deployment that already holds a secret it cannot re-hash.

Three properties matter, and all three are deliberate:

* **There is no route that creates the first administrator.** An unauthenticated
  "create the first admin" endpoint is a backdoor, not a bootstrap.
* **It is never overwritten from the environment.** Once it exists, a redeploy
  cannot undo a password rotation made in the app. Lost it? That is what
  `npm run create-admin -- --reset --password '…'` is for, and it is manual on
  purpose: an automatic reset would mean anyone who can set a variable on the
  host can take the account over at the next deploy.
* **It cannot mint a second one.** Once ANY administrator exists, changing
  `SUPER_ADMIN_EMAIL` does nothing but log a warning. Which addresses may sign
  in is decided inside the product from that point on.

More administrators are created from the app: a super admin creating a channel
names the account that will run it, and the two are created in one transaction —
a channel with no administrator would be one nobody could publish to.

## 4. Amazon S3 setup

1. **Create a bucket** in your chosen region. Leave **Block Public Access
   ON** — nothing in this design is ever public. Every read goes through a
   short-lived presigned URL.
2. **Keep the bucket private and unversioned.** Versioning would retain
   deleted violating media (§25) and inflate storage cost.
3. **Create an IAM user** (or, on EC2/ECS, a role and set
   `AWS_USE_INSTANCE_ROLE=true` and leave the keys empty) with this
   least-privilege policy — replace `BUCKET`:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "GoodPostObjectsOnly",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject",
        "s3:DeleteObject",
        "s3:AbortMultipartUpload",
        "s3:ListMultipartUploadParts"
      ],
      "Resource": "arn:aws:s3:::BUCKET/goodpost/*"
    },
    {
      "Sid": "ListOnlyOurPrefix",
      "Effect": "Allow",
      "Action": ["s3:ListBucket", "s3:ListBucketMultipartUploads"],
      "Resource": "arn:aws:s3:::BUCKET",
      "Condition": {
        "StringLike": { "s3:prefix": ["goodpost/*"] }
      }
    }
  ]
}
```

Notes on that policy:

- Every action is scoped to the `goodpost/` prefix. The backend cannot read,
  overwrite or delete anything else in the bucket, so a compromised key
  cannot damage unrelated data.
- `s3:ListBucket` is included only for the orphan-cleanup job (§34) and is
  itself restricted to the one prefix.
- No `s3:DeleteBucket`, no `s3:PutBucketPolicy`, no wildcard resources.
- Presigned URL *generation* needs no extra permission — the signature is
  computed locally — so this policy does not need to grant one.

4. **CORS** is only needed if a *browser* uploads directly with a presigned
   URL. The Android app and the direct-to-bucket path need none, and nothing
   here is browser-facing, so a deployment with no browser client needs no CORS
   at all. If one is ever added, and it uploads directly, allow:

```json
[
  {
    "AllowedOrigins": ["https://admin.your-domain.example"],
    "AllowedMethods": ["PUT", "GET"],
    "AllowedHeaders": ["*"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3000
  }
]
```

5. **Lifecycle rule** (optional, recommended): abort incomplete multipart
   uploads after 7 days. This is the only automatic S3 deletion the design
   wants — our own cleanup handles referenced objects (§34).

### Object layout

```
goodpost/
  channels/<channelId>/posts/<postId>/<mediaId>.<ext>
  channels/<channelId>/icons/<hash>.<ext>
  users/<userId>/avatars/<hash>.<ext>
```

Deleting a post deletes its objects by exact key. Objects are never shared
between rows, so a delete can never orphan a still-referenced file — that is
a deliberate schema property, not an accident.

## 5. Render deployment

`render.yaml` is a Blueprint: Render → **New → Blueprint** → select this repo.
It sets the build/start commands, the health check path, `rootDir: server`,
and prompts once for each `sync: false` variable.

**Region: `frankfurt`** (Render's eu-central-1). Neon and S3 are both in
`eu-central-1`, so this keeps every hop in one region. Put the Render service
anywhere else and every query and every upload crosses the Atlantic.

If you would rather configure by hand:

| Setting | Value |
|---|---|
| Root Directory | `server` |
| Build Command | `npm ci --include=dev && npm run build` |
| Pre-deploy Command | `npm run migrate:prod` — **paid plans only**, see below |
| Start Command | `npm start` |
| Health Check Path | `/health` |
| Region | `Frankfurt (EU Central)` |

### Why the build command says `--include=dev`

`typescript` and the `@types/*` packages are **devDependencies**, which is
correct — they are build-time tooling, not runtime dependencies.

But `NODE_ENV=production` makes `npm ci` omit devDependencies, and this service
sets `NODE_ENV=production`. The failure is confusing rather than obvious: the
build does not say *"tsc: not found"*, it prints dozens of `TS7016: Could not
find a declaration file for module 'express'` errors, because the type packages
are missing while the JavaScript they annotate is installed.

`--include=dev` makes the build independent of that setting. If you ever see
those `TS7016` errors again, this flag is the first thing to check — in
`render.yaml` *and* in the dashboard, since a manually-edited service ignores
the file.

### Free plan: no Shell, no pre-deploy

`render.yaml` uses the **free** instance. Two of its limits change how you
deploy, and neither has a workaround on Render's side:

- **No pre-deploy command.** It is a paid feature. So nothing runs migrations
  as part of a deploy.
- **No Shell access** (neither SSH nor the dashboard). So there is no way to
  run them from inside Render afterwards either.

Run migrations **from your machine**, against Neon directly:

```bash
cd server
npm run migrate      # reads DATABASE_URL_DIRECT from server/.env
```

That is not a hack. Neon is external to Render either way, migration files are
immutable and checksummed, re-running them is a no-op, and each runs in its own
transaction under a session-level advisory lock. Run it before deploying a
commit that needs a new migration.

A consequence worth noting: on the free plan **`DATABASE_URL_DIRECT` does not
need to be set on Render at all** — only `DATABASE_URL`, which the service is
required to have.

The other free-plan behaviour to design around: the service **spins down after
15 minutes** without inbound traffic, and the next request pays a **cold start
of roughly a minute**. The Android client uses a 15-second read timeout, so the
first Good Post request after a pause will report `unreachable` and succeed on
the retry. Render's own documentation says of Free instances: *"Do not use them
for production applications."*

To move to a paid instance: set `plan: starter` in `render.yaml` and restore
`preDeployCommand: npm run migrate:prod` (the exact lines are in the comments
there).

### Migration safety on a hosted database

`migrate:prod` uses `DATABASE_URL_DIRECT`, not `DATABASE_URL`. Migrations take
a **session-level advisory lock**; a transaction pooler may route one session
across backend connections, which breaks the lock that stops two deploys from
migrating at once. The app itself uses the pooled `DATABASE_URL`. On a paid
plan Render needs both variables; on the free plan only `DATABASE_URL` is set
on Render, because the migration runs from your machine.

### Environment variables Render must receive

`render.yaml` declares all of these. Values marked **generated** are created by
Render — never invent or paste them by hand.

| Variable | Source |
|---|---|
| `DATABASE_URL` | you paste (Neon **pooled**, host contains `-pooler`) |
| `DATABASE_URL_DIRECT` | you paste (Neon **direct**) |
| `SUPER_ADMIN_EMAIL` | you paste — the account that can publish (§3) |
| `SUPER_ADMIN_PASSWORD_HASH` | you paste — a bcrypt hash, NOT re-hashed by the server |
| `ADMIN_CONTACT_EMAIL` | you paste — shown by the app's "Don't have channel access?" line |
| `JWT_SECRET` | **generated** (`generateValue: true`) |
| `JWT_REFRESH_SECRET` | **generated** |
| `PHONE_HASH_PEPPER` | **generated** |
| `NODE_ENV` | `production` |
| `PUBLIC_BASE_URL` | the service's own `onrender.com` URL |

Optional tuning, defaulted in `src/env.ts`: `ADMIN_ACCESS_TOKEN_TTL`,
`ADMIN_SESSION_TTL_DAYS`, `ADMIN_MIN_PASSWORD_LENGTH`,
`GOODPOST_HISTORY_DAYS`, `MAX_POST_MEDIA`, `MAX_TEXT_LENGTH`,
`RATE_LIMIT_MAX`, `RATE_LIMIT_WINDOW_MS`, `AUTH_RATE_LIMIT_MAX`,
`WRITE_RATE_LIMIT_MAX`, `LOGIN_MAX_FAILED_ATTEMPTS`, `LOGIN_LOCKOUT_MINUTES`.
S3 variables are optional: their absence is a supported deployment, not a
misconfiguration (§22).

`src/env.ts` **refuses to start** in production without `SUPER_ADMIN_EMAIL` and
a password for it. A service nobody can sign in to is a channel list that never
changes, and that is worth failing a deploy over. A mismatched or placeholder
`JWT_SECRET` is refused for the same reason.

> **Never set `PHONE_HASH_PEPPER` to a new value on an existing database.** It
> is the pepper behind every IP hash in the audit log, so changing it makes
> those unreadable rather than wrong — but the log is append-only, so the old
> rows stay exactly as they are and only new ones differ.

**Health endpoints**

| Endpoint | Meaning |
|---|---|
| `GET /health` | Process is serving. **Does not touch the database** — Render restarts a service whose health check fails, so a brief Neon suspend must not restart a healthy process. |
| `GET /health/db` | `200 {ok:true}` or `503 {ok:false}`. Readiness only; safe to point monitoring at it. |

## 6. Android production configuration

The app needs exactly one backend value — a base URL — and **no secrets**.

Set it in `gradle.properties` (the file is committed; a public hostname is not
a secret):

```properties
goodPostBaseUrl=https://your-service.onrender.com
```

Or override it for a single build:

```bash
./gradlew assembleDebug -PgoodPostBaseUrl=https://your-service.onrender.com
```

`app/build.gradle.kts` turns it into `BuildConfig.GOODPOST_BASE_URL`.

**It is deliberately empty by default, and that is a feature.** A build must
not silently point at a developer's machine, an expired Cloudflare tunnel or a
stale preview URL. While it is empty, the Good Post tab says *"not set up in
this build"* instead of failing with a confusing network error.

Never hard-code `localhost` for a release build (§41), and never put a
credential here — `gradle.properties` is readable from the APK.

## 8. HTTP API surface

Two prefixes, and the split is the product (§24):

* **`/api/v1` — everything a reader fetches, anonymously, read-only.** No route
  here requires a token, and none may ever accept one as an authority. There is
  no write route in that module to authorise, so the worst a caller can do is
  read something published to the world on purpose.
* **`/admin/api` — everything an administrator changes, bearer token only.** A
  different token audience AND a different signing key from anything a reader
  sees, so neither surface can be reached from the other by guessing a path.

Errors are `{ "error": "<machine_code>" }`; the client branches on the code,
never on prose. The common ones are `channel_not_found`, `invalid_cursor`,
`media_unavailable`, `invalid_credentials`, `admin_locked`,
`admin_forbidden`, `media_not_ready` and `unknown_media`.

### Reader surface (`/api/v1`)

| Method | Path | Purpose |
|---|---|---|
| GET | `/channels` | Channel list and search (§3, §6, §7) |
| GET | `/categories` | Categories an Explore filter can offer (§7) |
| GET | `/channels/:idOrSlug` | One channel, by uuid or share slug |
| GET | `/channels/:idOrSlug/posts` | Its history, newest first (§9) |
| GET | `/channels/:idOrSlug/media` | Its images and videos (§13) |
| GET | `/posts/:postId` | One post, with the channel it came from |

Query parameters: `q` (name/description substring), `category`, `sort`
(`recent` \| `name`), `limit`, `cursor`. Paged with an opaque keyset cursor —
pass the `nextCursor` from the previous response straight back to resume. A
malformed cursor is `invalid_cursor` (400) rather than a silent restart from
page one. There is no `popular` sort and no ranking beyond recency: popularity
would have to mean follower count, and no follower count exists (§1).

### Administrator surface (`/admin/api`)

| Method | Path | Purpose |
|---|---|---|
| POST | `/auth/login` | Email + password → access token, refresh token, role (§16) |
| POST | `/auth/refresh` | Rotate the refresh token; a replay revokes every session |
| POST | `/auth/logout` | End this session |
| GET | `/auth/me` | Who am I, and what may I do |
| GET | `/channels` | The channels this account may publish to (§18) |
| POST | `/channels` | Create a channel, and the login that runs it (§20) |
| GET | `/channels/:channelId` | One channel, in scope |
| PATCH | `/channels/:channelId` | Edit name / description / category |
| POST | `/channels/:channelId/status` | Suspend or re-enable (super admin, §17) |
| DELETE | `/channels/:channelId` | Soft-delete (super admin) |
| GET | `/channels/:channelId/posts` | Its posts, including on a suspended channel |
| POST | `/channels/:channelId/posts` | Publish (§21) |
| PATCH | `/posts/:postId` | Edit text or link |
| DELETE | `/posts/:postId` | Soft-delete, so it stays reversible |
| POST | `/media/uploads` | Presigned PUT URL + media id (§21) |
| POST | `/media/uploads/:mediaId/confirm` | Let the server HEAD the object; then it may be attached |
| GET | `/admins` \| POST `/admins` | List, and create a channel administrator (§18) |
| POST | `/admins/:adminId/status` | Disable or re-enable (§27) |
| GET | `/audit` | The append-only audit log (§29) |
| GET | `/settings` | Effective, non-secret configuration |

Writes carry the `write` rate-limit rule; `/auth/login` carries the tighter
`auth` rule and, separately, a per-IDENTITY lockout.

### Publishing media (§21, §22)

Three steps, in this order: **presign → PUT → confirm**. The client never sees
an AWS credential and never chooses an object key — it is derived from a uuid
the server generates, so a request cannot name where its bytes land. The PUT
goes straight to the bucket, so a hundred-megabyte video never passes through
this process.

`contentType` and `byteSize` are SIGNED into the upload URL, so the bucket
itself rejects a different type or a larger file. The confirm step then HEADs
the object: "the client says it uploaded" is not evidence, and a post can never
carry an asset that was never really there.

A post's `type` is DERIVED from what is attached, never accepted from the
client — a client that said `video` while attaching a JPEG would describe its
own post wrongly and every reader would render it wrongly.

### Channel and post payloads

No payload on either surface contains a follower count, post count, reaction,
view total or owner — those columns were dropped in migration 012, so the
shapes have nowhere to put them. `shareLink` is an app deep link
(`clearview://goodpost/channel/<slug>`), because this service serves JSON and
handing the client an `https://` URL that 404s would be worse.

A post's media carries a short-lived signed read URL, or `null` on a deployment
with no bucket: one unservable asset must not fail the whole screen.

## 9. Code layout

```
server/
  migrations/         forward-only SQL, checksummed, applied in filename order
  src/
    env.ts            validated configuration; refuses placeholder secrets in production
    db.ts             pg pools, query helpers, transactions
    app.ts            Express app factory (no listen — drives tests directly)
    index.ts          listen, retention schedule, graceful shutdown
    migrate.ts        migration runner
    public/           the anonymous read surface (§24); routes + post/media reads
    channels/         the channels table for BOTH surfaces; slug and cursor are pure and unit-tested
    posts/            publishing, editing and removing a post (§21)
    media/            the upload lifecycle and the object store (§21, §22)
    admin/            sign-in, sessions, roles, audit, and the admin API (§16–§19)
    jobs/retention.ts post-history retention sweep (§11)
    retention/purge.ts
  tests/              vitest + supertest, against real SQL on an in-process Postgres
  scripts/
    normalize-env.mjs     strip stacked quotes that `dotenv` would leave behind
  render.yaml         Render Blueprint
```

### Why `.env` has its own tooling

`.env` is a plain text file, and shell quoting silently corrupts it. A value
written as `KEY='"postgresql://…"'` gets ONE quote layer stripped by `dotenv`,
leaving a literal `"` at each end of the URL. It still *looks* correct in an
editor, but the driver sees a hostname of `base`. `npm run env:check` detects
that class of damage and `npm run env:fix` repairs it — verifying the whole
file re-parses to the intended values **before** anything is written.

## 10. Security invariants

These hold across every endpoint and are enforced **server-side** (§25, §29):

1. The backend is the only authority on role and scope. Nothing
   client-supplied about an account, its role or its channel is ever trusted:
   the role is re-read from `admin_users` on every request, and a channel
   administrator's scope comes from their own row, not from the URL.
2. A channel a channel administrator may not touch answers **404, not 403**.
   Telling them a channel exists but is not theirs would confirm a channel they
   have no business knowing about.
3. The admin surface has a separate path prefix, token audience AND signing key
   from the reader surface — neither token can satisfy the other's check even
   if the endpoint path is guessed.
4. No plaintext password, access token or AWS credential is ever logged, and no
   password hash is ever serialised: `AdminAccount` has nowhere to put one.
5. Every protected endpoint re-checks: token verifies → session still live →
   account still active → role permits this exact action → the channel is in
   scope. Hiding a button in the app is never the control.
6. Passwords are bcrypt with a per-row salt, and a sign-in for an address that
   does not exist still runs a comparison, so the response time cannot be used
   to discover which addresses exist.
