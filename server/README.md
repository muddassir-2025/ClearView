# ClearView Good Post — Backend

A WhatsApp-Channels-style broadcasting service for the ClearView Android app.
Node 22 + TypeScript + Express 5, **Neon PostgreSQL** for structured data,
**Amazon S3** for media, deployed on **Render**.

The Android app is in the repository root (`app/`). **This `server/`
directory is the whole backend** — it is a separate deployable, not part of
the Gradle build.

| 7 | `PUBLIC_BASE_URL` | Your Render URL, e.g. `https://clearview-goodpost-api.onrender.com` | M2 |
| 8 | `BOOTSTRAP_ADMIN_EMAIL` / `BOOTSTRAP_ADMIN_PASSWORD` | You choose | M6 |

`JWT_SECRET`, `JWT_REFRESH_SECRET` and `PHONE_HASH_PEPPER` are **generated by

```bash
node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
```

> **Never put any of these in the Android app, and never commit them.** The
> Android client only ever needs the backend base URL (see §6).

## 2. Neon PostgreSQL setup

1. Create a project at [neon.tech](https://neon.tech) (any region close to
   your Render region — pairing `frankfurt` with `aws-eu-central-1` keeps
   database round-trips short).
2. Copy **two** connection strings from the dashboard:
   - the **pooled** one (host contains `-pooler`) → `DATABASE_URL`
   - the **direct** one → `DATABASE_URL_DIRECT`
3. TLS is required; both strings end in `?sslmode=require`.

**Why two URLs.** The running service uses the pooled host so many short
requests share few Postgres connections. Migrations use the direct host: a
transaction-pooling endpoint may route the statements of one logical session
across different backends, which breaks both DDL and the session-level
advisory lock the migration runner depends on (§42).

### Migrations

Never mutate the production schema at startup (`server/src/index.ts` does not
do this, by design). Migrations are forward-only SQL files in `migrations/`,
applied by `src/migrate.ts`:

```bash
npm run migrate          # local, via tsx
npm run migrate:prod     # compiled, via dist/migrate.js — what Render runs
```

The runner:

- wraps **each file in its own transaction** — a migration fully applies or
  not at all;
- takes a **session advisory lock** so two concurrent runs cannot race (a
  Render pre-deploy can overlap a still-draining instance);
- records a **SHA-256 checksum** of each applied file and refuses to run if an
  applied file changed. Migrations are immutable — add a new file instead;
- is **idempotent** — re-running with nothing to apply exits cleanly.

### Backup / rollback

Neon keeps point-in-time-restore history per branch, which is the rollback
mechanism: restore the branch to a timestamp rather than writing `DOWN`
migrations. Before a risky migration, create a Neon branch of production
first, and run the migration against that branch to verify it.

## 3. Firebase Phone Auth setup

1. Firebase Console → your project → **Add app → Android**, with the package
   that the **installed build actually uses**.

   > **The package name selects the Firebase app entry — it is not cosmetic.**
   > `app/build.gradle.kts` currently applies `applicationIdSuffix = ".debug"`,
   > so an Android Studio debug build is `com.muddassir.clearview.debug` and
   > Firebase matches it against the **`.debug`** entry. A production build is
   > `com.muddassir.clearview`. Register the SHA against the same entry the
   > build resolves to, or Phone Auth fails with `ERROR_APP_NOT_AUTHORIZED`.
   > Removing the suffix is a one-line switch to production parity; see the
   > comment at that line.

2. Add the **SHA-1** and **SHA-256** of the signing key used to install the
   app (Debug: `./gradlew signingReport`; Release: your upload key) **to that
   same entry**. Phone Auth silently fails without these.

   Signing certs live only in the console — they are **not** stored in
   `google-services.json`, so adding a SHA never requires re-downloading it.
3. **Build → Authentication → Sign-in method → Phone → Enable.**
4. **Project settings → Service accounts → Generate new private key.**

   Do not hand-edit the JSON into `.env` — a mistake there is silent and the
   private key spans 28 lines once its `\n` escapes are unpacked. Use the
   importer, which writes safely, **never prints the value**, and verifies the
   round-trip:

   ```bash
   cd server
   npm run firebase:env -- ~/Downloads/your-service-account.json
   ```

   It writes `FIREBASE_PROJECT_ID`, `FIREBASE_CLIENT_EMAIL` and
   `FIREBASE_PRIVATE_KEY` into `.env` (gitignored) and is idempotent, so it
   doubles as the tool for a future key rotation.
5. **Prove the credentials actually work** — presence is not proof:

   ```bash
   npm run firebase:verify
   ```

   This initialises the Admin SDK, mints a real signed token, and confirms
   that malformed, expired and tampered tokens are all rejected with a
   *signature* error (not a network one). It prints no key material.

6. Budget: Firebase's free tier includes a small number of SMS verifications
   per day. Enable **App Check** and abuse protection before launch.

**How the flow works.** Firebase sends and checks the SMS code on the device.
The device then sends us the resulting Firebase **ID token**; the backend
verifies that token with the Admin SDK, extracts the phone number, and stores
only `HMAC-SHA256(E.164, PHONE_HASH_PEPPER)` — never the number itself (§38).
That hash is the identity that mobile-number bans attach to (§19).

## 4. Amazon S3 setup

1. **Create a bucket** in your chosen region. Leave **Block Public Access
   ON** — nothing in this design is ever public. Every read goes through a
   short-lived presigned URL.
2. **Keep the bucket private and unversioned.** Versioning would retain
   deleted violating media (§25) and inflate storage cost.
3. **Create an IAM user** (or, on EC2/ECS, a role and set
   `AWS_USE_INSTANCE_ROLE=true` and leave the keys empty) with this
   least-privilege policy — replace `BUCKET`:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "GoodPostObjectsOnly",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject",
        "s3:DeleteObject",
        "s3:AbortMultipartUpload",
        "s3:ListMultipartUploadParts"
      ],
      "Resource": "arn:aws:s3:::BUCKET/goodpost/*"
    },
    {
      "Sid": "ListOnlyOurPrefix",
      "Effect": "Allow",
      "Action": ["s3:ListBucket", "s3:ListBucketMultipartUploads"],
      "Resource": "arn:aws:s3:::BUCKET",
      "Condition": {
        "StringLike": { "s3:prefix": ["goodpost/*"] }
      }
    }
  ]
}
```

Notes on that policy:

- Every action is scoped to the `goodpost/` prefix. The backend cannot read,
  overwrite or delete anything else in the bucket, so a compromised key
  cannot damage unrelated data.
- `s3:ListBucket` is included only for the orphan-cleanup job (§34) and is
  itself restricted to the one prefix.
- No `s3:DeleteBucket`, no `s3:PutBucketPolicy`, no wildcard resources.
- Presigned URL *generation* needs no extra permission — the signature is
  computed locally — so this policy does not need to grant one.

4. **CORS** is only needed if a *browser* uploads directly with a presigned
   URL. The Android client and the server-side upload path need none. If the
   admin dashboard uploads large files directly (M6), add:

```json
[
  {
    "AllowedOrigins": ["https://admin.your-domain.example"],
    "AllowedMethods": ["PUT", "GET"],
    "AllowedHeaders": ["*"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3000
  }
]
```

5. **Lifecycle rule** (optional, recommended): abort incomplete multipart
   uploads after 7 days. This is the only automatic S3 deletion the design
   wants — our own cleanup handles referenced objects (§34).

### Object layout

```
goodpost/
  channels/<channelId>/posts/<postId>/<mediaId>.<ext>
  channels/<channelId>/icons/<hash>.<ext>
  users/<userId>/avatars/<hash>.<ext>
```

Deleting a post deletes its objects by exact key. Objects are never shared
between rows, so a delete can never orphan a still-referenced file — that is
a deliberate schema property, not an accident.

## 5. Render deployment

`render.yaml` is a Blueprint: Render → **New → Blueprint** → select this repo.
It sets the build/start commands, the health check path, `rootDir: server`,
and prompts once for each `sync: false` variable.

**Region: `frankfurt`** (Render's eu-central-1). Neon and S3 are both in
`eu-central-1`, so this keeps every hop in one region. Put the Render service
anywhere else and every query and every upload crosses the Atlantic.

If you would rather configure by hand:

| Setting | Value |
|---|---|
| Root Directory | `server` |
| Build Command | `npm ci --include=dev && npm run build` |
| Pre-deploy Command | `npm run migrate:prod` — **paid plans only**, see below |
| Start Command | `npm start` |
| Health Check Path | `/health` |
| Region | `Frankfurt (EU Central)` |

### Why the build command says `--include=dev`

`typescript` and the `@types/*` packages are **devDependencies**, which is
correct — they are build-time tooling, not runtime dependencies.

But `NODE_ENV=production` makes `npm ci` omit devDependencies, and this service
sets `NODE_ENV=production`. The failure is confusing rather than obvious: the
build does not say *"tsc: not found"*, it prints dozens of `TS7016: Could not
find a declaration file for module 'express'` errors, because the type packages
are missing while the JavaScript they annotate is installed.

`--include=dev` makes the build independent of that setting. If you ever see
those `TS7016` errors again, this flag is the first thing to check — in
`render.yaml` *and* in the dashboard, since a manually-edited service ignores
the file.

### Free plan: no Shell, no pre-deploy

`render.yaml` uses the **free** instance. Two of its limits change how you
deploy, and neither has a workaround on Render's side:

- **No pre-deploy command.** It is a paid feature. So nothing runs migrations
  as part of a deploy.
- **No Shell access** (neither SSH nor the dashboard). So there is no way to
  run them from inside Render afterwards either.

Run migrations **from your machine**, against Neon directly:

```bash
cd server
npm run migrate      # reads DATABASE_URL_DIRECT from server/.env
```

That is not a hack. Neon is external to Render either way, migration files are
immutable and checksummed, re-running them is a no-op, and each runs in its own
transaction under a session-level advisory lock. Run it before deploying a
commit that needs a new migration.

A consequence worth noting: on the free plan **`DATABASE_URL_DIRECT` does not
need to be set on Render at all** — only `DATABASE_URL`, which the service is
required to have.

The other free-plan behaviour to design around: the service **spins down after
15 minutes** without inbound traffic, and the next request pays a **cold start
of roughly a minute**. The Android client uses a 15-second read timeout, so the
first Good Post request after a pause will report `unreachable` and succeed on
the retry. Render's own documentation says of Free instances: *"Do not use them
for production applications."*

To move to a paid instance: set `plan: starter` in `render.yaml` and restore
`preDeployCommand: npm run migrate:prod` (the exact lines are in the comments
there).

### Migration safety on a hosted database

`migrate:prod` uses `DATABASE_URL_DIRECT`, not `DATABASE_URL`. Migrations take
a **session-level advisory lock**; a transaction pooler may route one session
across backend connections, which breaks the lock that stops two deploys from
migrating at once. The app itself uses the pooled `DATABASE_URL`. On a paid
plan Render needs both variables; on the free plan only `DATABASE_URL` is set
on Render, because the migration runs from your machine.

### Environment variables Render must receive

`render.yaml` declares all of these. Values marked **generated** are created by
Render — never invent or paste them by hand.

| Variable | Source |
|---|---|
| `DATABASE_URL` | you paste (Neon **pooled**, host contains `-pooler`) |
| `DATABASE_URL_DIRECT` | you paste (Neon **direct**) |
| `FIREBASE_PROJECT_ID` | you paste |
| `FIREBASE_CLIENT_EMAIL` | you paste |
| `FIREBASE_PRIVATE_KEY` | you paste (one line, literal `\n`) |
| `JWT_SECRET` | **generated** (`generateValue: true`) |
| `JWT_REFRESH_SECRET` | **generated** |
| `PHONE_HASH_PEPPER` | **generated** |
| `NODE_ENV` | `production` |
| `PUBLIC_BASE_URL` | the service's own `onrender.com` URL |

Optional tuning, defaulted in `src/env.ts`: `PHONE_VERIFY_MODE` (must be
`firebase` in production), `BAN_PHONE_ENFORCED` (must be `true` in production),
`ACCESS_TOKEN_TTL_MINUTES`, `REFRESH_TOKEN_TTL_DAYS`,
`GOODPOST_HISTORY_DAYS`, `RATE_LIMIT_MAX`, `RATE_LIMIT_WINDOW_MS`,
`AUTH_RATE_LIMIT_MAX`. S3 variables are not needed until M3.

`src/env.ts` **refuses to start** in production if the phone verifier is
`disabled`, if `BAN_PHONE_ENFORCED=false`, or if a `firebase` mode has no
credentials. A misconfigured deploy fails loudly at boot instead of silently
running with identity checks switched off.

> **Never set `PHONE_HASH_PEPPER` to a new value on an existing database.**
> It is the salt behind every stored phone hash, so changing it makes every
> existing ban identity unrecognisable — exactly the bypass §19 forbids.

**Health endpoints**

| Endpoint | Meaning |
|---|---|
| `GET /health` | Process is serving. **Does not touch the database** — Render restarts a service whose health check fails, so a brief Neon suspend must not restart a healthy process. |
| `GET /health/db` | `200 {ok:true}` or `503 {ok:false}`. Readiness only; safe to point monitoring at it. |

## 6. Android production configuration

The app needs exactly one backend value — a base URL — and **no secrets**.

Set it in `gradle.properties` (the file is committed; a public hostname is not
a secret):

```properties
goodPostBaseUrl=https://your-service.onrender.com
```

Or override it for a single build:

```bash
./gradlew assembleDebug -PgoodPostBaseUrl=https://your-service.onrender.com
```

`app/build.gradle.kts` turns it into `BuildConfig.GOODPOST_BASE_URL`.

**It is deliberately empty by default, and that is a feature.** A build must
not silently point at a developer's machine, an expired Cloudflare tunnel or a
stale preview URL. While it is empty, the Good Post tab says *"not set up in
this build"* instead of failing with a confusing network error.

Never hard-code `localhost` for a release build (§41), and never put a
credential here — `gradle.properties` is readable from the APK.

## 8. HTTP API surface

Everything lives under `/api/v1` and **every endpoint requires a session** —
there is no anonymous Good Post surface (§38). Send the access token as
`Authorization: Bearer <token>`.

Errors are `{ "error": "<machine_code>" }`; the client branches on the code,
never on prose. Common ones: `missing_token`, `invalid_token`,
`session_revoked`, `account_banned`, `account_suspended`.

### Identity (`/api/v1/auth`) — M1

| Method | Path | Purpose |
|---|---|---|
| POST | `/otp/request` | Claim the send allowance, then Firebase sends the SMS |
| POST | `/register` | Firebase ID token → account + session |
| POST | `/signin` | Same, for an existing account |
| POST | `/refresh` | Rotate the refresh token (replay is detected) |
| POST | `/logout` | Revoke this session, or all of them |
| GET | `/me` | The gate the client checks on entry |

### Channels (`/api/v1/channels`) — M2

| Method | Path | Purpose |
|---|---|---|
| GET | `/categories` | Enabled categories (§5) |
| GET | `/following` | Channels the caller follows (§4), cursor-paged |
| GET | `/mine` | Channels the caller owns or helps run (§7) |
| POST | `/` | Create a channel (§6) |
| GET | `/:channelId` | Channel detail + the caller's own relationship to it |
| PATCH | `/:channelId` | Edit name / description / category / country (§7, owner only) |
| POST | `/:channelId/follow` | Follow (§12) |
| DELETE | `/:channelId/follow` | Unfollow |
| PUT | `/:channelId/notifications` | Mute / unmute (§17) |
| POST | `/:channelId/read` | Clear the unread flag (§4) |
| POST | `/:channelId/block` | Block, which also ends the follow (§12) |
| DELETE | `/:channelId/block` | Unblock |

Writes carry the `write` rate-limit rule (`WRITE_RATE_LIMIT_MAX`).

### Discovery (`/api/v1/discover`) — M2

| Method | Path | Purpose |
|---|---|---|
| GET | `/channels` | Search + browse (§5) |

Query parameters: `q` (name/description substring), `category`, `country`
(ISO-3166-1 alpha-2), `sort` (`popular` \| `active` \| `new`), `limit`,
`cursor`. Paged with an opaque keyset cursor — pass the `nextCursor` from the
previous response straight back to resume. A malformed cursor is
`invalid_cursor` (400) rather than a silent restart from page one.

Ranking is followers × recent activity (§5). There is no recommender.

### Channel payloads

A channel payload never contains owner or follower identity (§12, §38):
`owner_id` is read for authorization and never serialised, and there is no
endpoint that lists a channel's followers. `shareLink` is currently an app
deep link (`clearview://goodpost/channel/<slug>`); public read-only channel
pages are an open decision — see `docs/GOODPOST_PLAN.md` §5.3.

## 9. Code layout

```
server/
  migrations/         forward-only SQL, checksummed, applied in filename order
  src/
    env.ts            validated configuration; refuses placeholder secrets in production
    db.ts             pg pools, query helpers, transactions
    app.ts            Express app factory (no listen — drives tests directly)
    index.ts          listen, retention schedule, graceful shutdown
    migrate.ts        migration runner
    auth/             Firebase verification, JWT + refresh tokens, middleware
    channels/         channels + discovery; slug and cursor are pure and unit-tested
    jobs/retention.ts post-history retention sweep (§11) — stub until M7
  tests/              vitest + supertest
  scripts/
    set-firebase-env.mjs  import a service-account JSON into .env (§3)
    verify-firebase.ts    prove the Admin SDK can sign, and reject bad tokens
    normalize-env.mjs     strip stacked quotes that `dotenv` would leave behind
  render.yaml         Render Blueprint
```

### Why `.env` has its own tooling

`.env` is a plain text file, and shell quoting silently corrupts it. A value
written as `KEY='"postgresql://…"'` gets ONE quote layer stripped by `dotenv`,
leaving a literal `"` at each end of the URL. It still *looks* correct in an
editor, but the driver sees a hostname of `base`. `npm run env:check` detects
that class of damage and `npm run env:fix` repairs it — verifying the whole
file re-parses to the intended values **before** anything is written.

## 10. Security invariants

These hold across every endpoint and are enforced **server-side** (§32, §38):

1. The backend is the only authority on identity, ownership and roles. Nothing
   client-supplied about an account, its role, or a channel's ownership is
   ever trusted.
2. No response contains another user's phone number or email. Phone numbers
   exist in plaintext only in memory, between Firebase verifying them and
   `hashPhone` persisting them.
3. Admin routes are a separate surface with a separate token audience from
   Good Post user routes — a normal user token cannot satisfy an admin check
   even if the endpoint path is guessed (§48).
4. No plaintext password, OTP, access token or AWS credential is ever logged.
5. Every protected endpoint re-checks: authenticated → active account → owns
   or manages the resource → role permits this exact operation. Ownership of
   a channel grants no platform-admin capability (§7).
